# Інкапсуляція

**Блок:** Блок 2. Методи та основи ООП
**Код заняття:** `020-oop-osnovy/060-inkapsuliatsiia.md`
**Тривалість:** 1.5–2 год
**Статус:** 🟢 розписано детально

## Опис
Модифікатори доступу (private/public), гетери/сетери.

## Мета заняття
- Розуміти ідею інкапсуляції: захист внутрішнього стану об'єкта від некоректних змін ззовні
- Вміти оголошувати приватні (`private`) поля з публічними гетерами/сетерами
- Вміти писати сетер, що перевіряє (валідує) значення перед присвоєнням

## Структура заняття

### 1. Хук / мотивація (5–10 хв)
Запитати групу: «Уявіть банківський рахунок, реалізований класом, де поле `balance` — звичайне публічне поле. Що завадить будь-якому коду написати `account.balance = -1000000;` напряму?» (Відповідь: нічого не завадить — і це проблема). Запустити [`BankAccountDemo.java`](src/060-inkapsuliatsiia/BankAccountDemo.java) — показати, що зняття суми, більшої за баланс, коректно відхиляється методом, а не ламає програму.

### 2. Коротка теорія (15–20 хв)
**Модифікатори доступу.** `public` — поле чи метод доступні звідусіль. `private` — доступні лише всередині цього самого класу. Досі всі поля в наших класах (`Dog`, `Book`, `Student`) фактично мали доступ за замовчуванням (без модифікатора) — це працювало, але не захищало дані від некоректних змін ззовні.

**Ідея інкапсуляції.** Робимо поля `private`, а доступ до них — лише через спеціальні публічні методи:
- **Гетер (getter)** — метод, що повертає значення поля: `double getBalance() { return balance; }`.
- **Сетер (setter)** — метод, що встановлює нове значення поля, за потреби з перевіркою (валідацією):
```java
void setAge(int age) {
    if (age < 0) {
        System.out.println("Вік не може бути від'ємним, значення не змінено.");
        return;
    }
    this.age = age;
}
```
Якщо поле `private`, рядок `person.age = -5;` ЗЗОВНІ класу навіть не скомпілюється — змінити вік можна лише через `setAge()`, а той сам вирішує, чи коректне значення.

**Чому це важливо в реальній розробці.** Інкапсуляція — один з чотирьох базових принципів ООП (разом з наслідуванням, поліморфізмом і абстракцією, які розглянемо далі в цьому блоці). Вона дозволяє класу самому гарантувати, що його внутрішній стан завжди залишається коректним, незалежно від того, який зовнішній код його використовує.

### 3. Демонстрація / live-coding (15–20 хв)

### 4. Керована практика (20–30 хв)
Разом розібрати пару [`Person.java`](src/060-inkapsuliatsiia/Person.java) + [`PersonDemo.java`](src/060-inkapsuliatsiia/PersonDemo.java) — приватні поля `name`/`age`, гетери для обох, сетер лише для `age` з валідацією (не може бути від'ємним).

### 5. Самостійна практика / челендж (20–30 хв)
Розібрати й доповнити пару [`Product.java`](src/060-inkapsuliatsiia/Product.java) + [`ProductDemo.java`](src/060-inkapsuliatsiia/ProductDemo.java) — приватні поля `price`/`quantity` з валідацією в сетерах, метод `getTotalCost()`. Челендж: додати перевірку — кількість не може перевищувати, скажімо, 1000 одиниць (штучне обмеження складу).

### 6. Рефлексія та підсумок (5–10 хв)
Обговорити на прикладі з хука: якби `BankAccount.balance` було `public`, які реальні проблеми могли б виникнути в банківському застосунку? Закріпити правило за замовчуванням: «поля — `private`, доступ — через методи», якщо немає особливої причини робити інакше.
