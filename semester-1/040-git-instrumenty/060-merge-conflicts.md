# Merge conflicts

**Блок:** Блок 4. Git та інструменти розробника
**Код заняття:** `040-git-instrumenty/060-merge-conflicts.md`
**Тривалість:** 1.5–2 год
**Статус:** 🟢 розписано детально

## Опис
Що це і як вирішувати.

## Мета заняття
- Розуміти, чому й коли виникає конфлікт злиття (merge conflict)
- Вміти прочитати маркери конфлікту в файлі
- Вміти вручну вирішити конфлікт і завершити злиття

## Підготовка викладача (перед заняттям)
Весь сценарій цього заняття реально відтворений і перевірений заздалегідь — точні команди та вивід знаходяться в [`src/060-merge-conflicts/`](src/060-merge-conflicts/). Варто самостійно пройти сценарій ще раз перед заняттям, щоб впевнено відповідати на запитання під час демонстрації.

## Структура заняття

### 1. Хук / мотивація (5–10 хв)
Запитати: «Уявіть: ви і колега одночасно редагуєте ТОЙ САМИЙ рядок коду в різних гілках. Один із вас зливає свою гілку в `main` першим. Що станеться, коли другий спробує зробити те саме?» Git не може сам вирішити, чию версію лишити — це і є конфлікт злиття.

### 2. Коротка теорія (15–20 хв)
**Коли виникає конфлікт.** Git автоматично зливає зміни, якщо вони стосуються РІЗНИХ місць файлу (або різних файлів). Конфлікт виникає, коли ДВІ гілки змінили той самий рядок (або сусідні рядки) по-різному — Git не може вгадати, яку версію ви хочете залишити, і зупиняє злиття, чекаючи рішення людини.

**Як виглядає конфлікт (реальний, перевірений приклад).** Дві гілки, `feature/stepin` і `feature/ostacha`, обидві додають нову операцію в `calculate()` в ОДНЕ Й ТЕ САМЕ місце коду (перед `default:`). Спроба `git merge feature/ostacha` (коли `feature/stepin` вже змержено в `main`) дає:
```
Auto-merging Calculator.java
CONFLICT (content): Merge conflict in Calculator.java
Automatic merge failed; fix conflicts and then commit the result.
```

Файл після цього виглядає так (фрагмент, повний приклад — [`src/060-merge-conflicts/conflict-markers-example.txt`](src/060-merge-conflicts/conflict-markers-example.txt)):
```
            case "/":
                return a / b;
<<<<<<< HEAD
            case "^":
                return Math.pow(a, b);
=======
            case "%":
                return a % b;
>>>>>>> feature/ostacha
            default:
```

**Маркери конфлікту:**
- `<<<<<<< HEAD` — початок версії з ПОТОЧНОЇ гілки (куди зливаємо, тут — `main`, де вже є `feature/stepin`).
- `=======` — роздільник між двома версіями.
- `>>>>>>> feature/ostacha` — кінець версії з гілки, яку намагаємось злити.

**Як вирішити конфлікт.** Відкрити файл, вручну відредагувати — прибрати ВСІ три маркери (`<<<<<<<`, `=======`, `>>>>>>>`) і залишити той код, який насправді має бути (одну версію, іншу, або комбінацію обох — як у нашому прикладі, де залишили ОБИДВІ нові операції). Потім:
```
git add Calculator.java
git commit
```
Git сам запропонує повідомлення коміту на кшталт "Merge branch 'feature/ostacha'" — можна залишити його або написати своє.

### 3. Демонстрація / live-coding (15–20 хв)
Відтворити наживо весь сценарій із [`src/060-merge-conflicts/`](src/060-merge-conflicts/): дві гілки з файлами [`Calculator-feature-stepin.java`](src/060-merge-conflicts/Calculator-feature-stepin.java) і [`Calculator-feature-ostacha.java`](src/060-merge-conflicts/Calculator-feature-ostacha.java), злиття першої, спроба злиття другої (конфлікт), редагування файлу до вигляду [`Calculator-resolved.java`](src/060-merge-conflicts/Calculator-resolved.java), завершення коміту.

### 4. Керована практика (20–30 хв)
Розбити групу на пари. Кожна пара клонує один і той самий (тестовий, не основний) репозиторій, обидва учасники створюють гілку від однієї й тієї самої точки, змінюють ОДИН і той самий рядок `Calculator.java` по-різному, обидва відправляють гілки на GitHub, один зливає свою гілку в `main` першим, другий — намагається злити свою й отримує справжній конфлікт. Разом проходять вирішення.

### 5. Самостійна практика / челендж (20–30 хв)
Кожен студент самостійно (без пари) відтворює конфлікт на власному репозиторії з `Calculator.java`: дві власні гілки, що змінюють той самий рядок, злиття, конфлікт, вирішення. Челендж: спробувати `git merge --abort` посеред конфлікту (до вирішення) — переконатись, що це повністю скасовує спробу злиття і повертає репозиторій до стану "до merge", без жодних наслідків.

### 6. Рефлексія та підсумок (5–10 хв)
Обговорити: чи варто боятись конфліктів? (Відповідь: ні — це нормальна, очікувана частина командної роботи, а не ознака того, що щось "пішло не так" фатально). Головне — уважно читати обидві версії перед тим, як вирішувати, яку залишити.

## Домашнє завдання (необов'язково)
Навмисно створити ще один конфлікт (наприклад, дві гілки, що по-різному змінюють текст одного й того самого повідомлення `println`) і самостійно його вирішити без підказок.
