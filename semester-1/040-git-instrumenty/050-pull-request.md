# Командна робота: Pull Request

**Блок:** Блок 4. Git та інструменти розробника
**Код заняття:** `040-git-instrumenty/050-pull-request.md`
**Тривалість:** 1.5–2 год
**Статус:** 🟢 розписано детально

## Опис
Основи code review, як оформити PR.

## Мета заняття
- Розуміти, що таке Pull Request (PR) і навіщо він потрібен у командній роботі
- Вміти оформити PR на GitHub: гілка → push → відкриття PR → злиття через веб-інтерфейс
- Розуміти базову ідею code review (перегляду коду)

## Структура заняття

### 1. Хук / мотивація (5–10 хв)
Запитати: «На занятті 030 ми зливали гілки командою `git merge` локально, сам на сам зі своїм кодом. А якщо працює ціла команда — чи можна просто так брати й зливати будь-чий код у спільний `main` без жодного погляду з боку?» Pull Request — це саме "прошу перевірити мої зміни, перш ніж вони потраплять у спільний код".

### 2. Коротка теорія (15–20 хв)
**Що таке Pull Request (PR).** Запит на GitHub: «я зробив(ла) зміни в окремій гілці, будь ласка, перегляньте їх і, якщо все гаразд, злийте (merge) у `main`». PR показує весь diff (різницю) змін у зручному веб-інтерфейсі, дозволяє залишати коментарі до конкретних рядків коду, і лише після схвалення зміни потрапляють у основну гілку.

**Чому не просто `git push` напряму в `main`.** У командах з кількох людей прямий `push` у `main` без перегляду — ризикований: легко випадково зламати щось, що впливає на роботу всіх. PR додає "контрольну точку" перед тим, як зміни стають частиною спільного коду.

**Code review (перегляд коду).** Процес, коли інший розробник читає запропоновані зміни, шукає потенційні помилки, пропонує покращення чи просто питає уточнення — перш ніж погодити злиття. Це стандартна практика в переважній більшості професійних команд, а не формальність.

**Типовий життєвий цикл PR:**
1. Створити гілку з новою зміною, закомітити, `push` на GitHub.
2. Відкрити Pull Request на GitHub (порівнює вашу гілку з `main`).
3. Хтось (колега, ментор, або ви самі в навчальних цілях) переглядає diff, залишає коментарі за потреби.
4. Автор вносить правки, якщо були зауваження (новий коміт у ту саму гілку — PR оновлюється автоматично).
5. PR схвалюють і зливають (Merge pull request) — зміни потрапляють у `main`.

### 3. Демонстрація / live-coding (15–20 хв)
Наживо на своєму репозиторії з `Calculator.java`:
1. `git checkout -b feature/okruhlennia`
2. Додати в `calculate()` округлення результату до 2 знаків після коми, закомітити.
3. `git push -u origin feature/okruhlennia`
4. Перейти на GitHub — сайт сам запропонує жовту плашку "Compare & pull request" для щойно відправленої гілки. Натиснути.
5. Заповнити заголовок і короткий опис PR (що змінено і навіщо).
6. Показати вкладку "Files changed" — саме тут видно diff, і саме тут залишають коментарі до конкретних рядків.
7. Натиснути "Merge pull request" → "Confirm merge".
8. Локально: `git checkout main`, `git pull` — переконатись, що зміна "прийшла" з GitHub.

### 4. Керована практика (20–30 хв)
Кожен студент повторює цикл вище зі своєю власною невеликою зміною (нова операція, покращення тексту повідомлень тощо) — від створення гілки до злиття PR через GitHub.

### 5. Самостійна практика / челендж (20–30 хв)
Об'єднатись у пари. Кожен додає колегу як "Collaborator" до свого репозиторію (Settings → Collaborators на GitHub). Партнер клонує репозиторій, створює СВОЮ гілку з невеликим покращенням, відкриває PR у репозиторій колеги. Власник репозиторію переглядає PR і залишає щонайменше один коментар до конкретного рядка коду, перш ніж злити.

### 6. Рефлексія та підсумок (5–10 хв)
Обговорити відчуття "коли хтось інший читає твій код" — це нормальна й корисна частина роботи, а не привід для стресу. Гарний code review робить код кращим для всієї команди, а не є особистою критикою.

## Домашнє завдання (необов'язково)
Відкрити ще один PR із будь-якою дрібною зміною і самостійно написати змістовний опис PR (що зроблено, навіщо, як перевірити).
