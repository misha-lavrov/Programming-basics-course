# .gitignore, README, оформлення проекту

**Блок:** Блок 4. Git та інструменти розробника
**Код заняття:** `040-git-instrumenty/070-gitignore-readme.md`
**Тривалість:** 1.5–2 год
**Статус:** 🟢 розписано детально

## Опис
Гарні практики оформлення репозиторію.

## Мета заняття
- Розуміти, навіщо потрібен `.gitignore` і які файли туди варто додавати
- Вміти написати корисний `README.md` для свого проєкту
- Знати базові елементи "гарно оформленого" репозиторію

## Структура заняття

### 1. Хук / мотивація (5–10 хв)
Показати на екрані `git status` у щойно відкритому IntelliJ-проєкті — там, ймовірно, з'явиться підтека `.idea` та скомпільовані `.class`-файли як "untracked". Запитати: «Чи потрібні ці файли у спільній історії проєкту, якщо кожен розробник має свої особисті налаштування IDE?»

### 2. Коротка теорія (15–20 хв)
**Що таке `.gitignore`.** Текстовий файл у корені репозиторію, що каже Git: «ці файли/теки НІКОЛИ не пропонувати додавати, навіть якщо вони змінились». Типові кандидати:
- Налаштування IDE (`.idea/` для IntelliJ, `.vscode/` для VS Code) — особисті для кожного розробника, не мають сенсу в спільній історії.
- Скомпільовані файли (`*.class`, `out/`, `target/`) — можна перегенерувати з вихідного коду будь-коли, зберігати в git безглуздо.
- Секрети (паролі, ключі API) — **ніколи** не повинні потрапляти в git, навіть у приватний репозиторій.

Приклад реального `.gitignore` (саме такий використовується в цьому навчальному репозиторії з планом гуртка):
```
.idea
out/
```

**Створення `.gitignore` заднім числом.** Якщо файли з `.gitignore` вже потрапили в історію ДО того, як їх туди додали — сам `.gitignore` не прибере їх заднім числом автоматично, знадобиться додатково `git rm --cached <файл>`. Найкраще — створювати `.gitignore` одразу на самому початку проєкту, ще до першого коміту.

**`README.md`.** Перший файл, який бачить будь-хто, хто відкриває репозиторій на GitHub — сторінка автоматично показує його вміст під списком файлів. Хороший README відповідає на: що це за проєкт, як його запустити, які технології використано. Пишеться в форматі Markdown (`.md`) — те саме форматування, яким написані й самі файли занять цього курсу.

### 3. Демонстрація / live-coding (15–20 хв)
Наживо додати `.gitignore` у корінь репозиторію `Calculator.java`:
```
.idea
out/
*.class
```
Перевірити командою `git status` — теки `.idea`/`out` більше не пропонуються як untracked. Потім написати короткий `README.md`:
```markdown
# Java Calculator

Простий консольний калькулятор — навчальний проєкт для практики Git.

## Як запустити
javac Calculator.java
java Calculator
```
Закомітити обидва файли, відправити на GitHub (`git push`), оновити сторінку репозиторію в браузері — показати, що README тепер відображається під списком файлів.

### 4. Керована практика (20–30 хв)
Кожен студент додає `.gitignore` і `README.md` до свого репозиторію з `Calculator.java`. У README додатково описати, які операції підтримує калькулятор (`+ - * / ^ %`, зібрані за заняття 020–060).

### 5. Самостійна практика / челендж (20–30 хв)
Додати до README розділ "Автор" з посиланням на свій GitHub-профіль і бейдж (значок) — наприклад, через [shields.io](https://shields.io) — суто для практики: як вставляти зображення в Markdown (`![опис](посилання-на-зображення)`).

### 6. Рефлексія та підсумок (5–10 хв)
Обговорити: чому перше враження від репозиторію (README) важливе навіть для навчального проєкту — саме так виглядатиме портфоліо на GitHub, коли прийде час шукати першу роботу.

## Домашнє завдання (необов'язково)
Додати `.gitignore` і `README.md` до всіх попередніх навчальних проєктів (якщо вони теж викладені на GitHub) — блоків 1–3.
