# Базові команди

**Блок:** Блок 4. Git та інструменти розробника
**Код заняття:** `040-git-instrumenty/020-bazovi-komandy.md`
**Тривалість:** 1.5–2 год
**Статус:** 🟢 розписано детально

## Опис
init, add, commit, status, log.

## Мета заняття
- Вміти створити git-репозиторій (`git init`)
- Вміти зберігати зміни через `add` + `commit`
- Вміти переглядати стан репозиторію (`status`) та історію змін (`log`)

## Підготовка викладача (перед заняттям)
- Роздати або розмістити в спільному доступі стартовий файл [`Calculator.java`](src/practice-project/Calculator.java) — з цього заняття й до кінця блоку студенти працюватимуть саме з ним.

## Структура заняття

### 1. Хук / мотивація (5–10 хв)
Показати на екрані структуру теки з файлами `проект.docx`, `проект_v2.docx`, `проект_final.docx` (продовження хука з минулого заняття). Сказати: «Сьогодні розв'яжемо цю проблему на практиці — за 4 команди».

### 2. Коротка теорія (15–20 хв)
**`git init`** — перетворює звичайну теку на git-репозиторій, створюючи приховану підтеку `.git`, де зберігається вся історія. Виконується ОДИН РАЗ на проєкт.

**Три стани файлу в Git:**
1. **Untracked / Modified** — файл існує в теці, але Git ще не відстежує (або відстежує, але бачить незбережені зміни).
2. **Staged** (індекс, "зона підготовки") — файл позначений "включити в наступний коміт" через `git add`.
3. **Committed** — зміни збережені в історії через `git commit`.

**`git add <файл>`** — переносить файл у стан "staged" (готовий до коміту). `git add .` додає ВСІ змінені файли одразу.

**`git commit -m "повідомлення"`** — зберігає всі staged-зміни як новий "знімок" (commit) в історії, з обов'язковим повідомленням, що описує, ЩО і НАВІЩО змінено.

**`git status`** — показує поточний стан: які файли untracked, які staged, які змінені, але ще не додані.

**`git log`** — показує історію комітів (`git log --oneline` — компактний однорядковий варіант, зручніший для щоденного перегляду).

### 3. Демонстрація / live-coding (15–20 хв)
Виконати наживо повний цикл на прикладі [`Calculator.java`](src/practice-project/Calculator.java) (реально перевірена послідовність команд і вивід):
```
git init
git status
# On branch main
# No commits yet
# Untracked files: Calculator.java

git add Calculator.java
git status
# Changes to be committed: new file: Calculator.java

git commit -m "Початкова версія калькулятора"
# [main (root-commit) 3e0f3a9] Початкова версія калькулятора
#  1 file changed, ... insertion(+)

git log --oneline
# 3e0f3a9 Початкова версія калькулятора
```
Звернути увагу на попередження `warning: in the working copy of 'Calculator.java', LF will be replaced by CRLF...` — це нормально на Windows (різниця в символах закінчення рядка між Windows і Unix-системами), не помилка, ігнорувати.

### 4. Керована практика (20–30 хв)
Кожен студент:
1. Створює теку проєкту, копіює туди [`Calculator.java`](src/practice-project/Calculator.java).
2. Виконує `git init`, `git add`, перший `git commit`.
3. Вносить невелику зміну в код (наприклад, змінює текст повідомлення `"Невідома операція"`), перевіряє `git status` до і після `git add`, робить другий коміт.
4. Переглядає історію через `git log --oneline` — має побачити два коміти.

### 5. Самостійна практика / челендж (20–30 хв)
Додати до `Calculator.java` виведення привітання на початку програми (`System.out.println("Ласкаво просимо до калькулятора!")`) і зробити третій коміт з описовим повідомленням. Челендж: подивитись різницю між двома останніми комітами командою `git diff HEAD~1 HEAD`.

### 6. Рефлексія та підсумок (5–10 хв)
Обговорити: чому повідомлення коміту (`-m "..."`) варто писати змістовно (`"Додав привітання при запуску"`), а не абияк (`"зміни"`, `"фікс"`) — за кілька місяців саме повідомлення допоможе зрозуміти історію проєкту, свою чи чужу.

## Домашнє завдання (необов'язково)
Продовжити роботу з `Calculator.java`: зробити ще 2–3 невеликі зміни з окремими змістовними комітами кожна (наприклад, додати перевірку ділення на нуль).
